# Additive platform features and parity

The Swift application remains the Apple implementation and the pinned Kotlin
checkout remains the official Android implementation. The new hosts are
additive features under `apps/`; neither native source tree is rewritten.

```text
protocol-conformance/       one reviewed wire contract
          |
web-preview/                portable codec, Noise, Nostr and mesh policies
       /        \
browser feature             Windows Electron host + native BLE/DPAPI port

apps/android/               pinned official Kotlin build, kept separate
bitchat/                    original Apple application
```

Platform-specific Bluetooth and key storage stay behind small ports. Packet
encoding, validation, fragmentation, relay policy and file limits are shared.
This keeps reuse at the protocol boundary without inventing a universal native
application framework.

## Effective parity matrix

`Native` means the platform owns the complete application behavior. `Active`
means the Desktop/Web feature consumes and exposes it. `Relay only` means the
wire type can cross a Windows multi-peer mesh after bounded validation, but the
Desktop UI does not implement its business workflow.

| Capability | Apple base | Official Android pin | Windows Desktop | Browser |
| --- | --- | --- | --- | --- |
| BLE mesh role | Native | Native | Native GATT peripheral, multi-central | Central gateway only |
| Announce / leave / public text | Native | Native | Active | Active through one selected BLE link |
| Noise XX private text | Native | Native | Active | Active through one selected BLE link |
| Delivered / read receipts | Native | Native | Active | Active |
| Public and private files/images | Native | Native | Active, images optimized and native limits enforced | Active when BLE is available |
| Classic voice-note file | Native recorder/player | Native recorder/player | Active recorder/player over the shared file transport | Active when BLE is available |
| Live push-to-talk frames | Native | Native wire type | Relay only | Not active |
| Nostr public/private messages | Native | Native | Active | Active |
| Courier store-and-forward | Native | Not in the pinned Android `MessageType` | Directed signed relay only; no storage workflow | Not active |
| Group state/messages | Native | Apple wire types absent from the pin | Bounded opaque relay only | Not active |
| Board posts / prekeys | Native | Apple wire types absent from the pin | Signed opaque relay only | Not active |
| Ping / pong diagnostics | Native | Apple wire types absent from the pin | Bounded directed relay only | Not active |
| Nostr carrier gateway packet | Native | Apple wire type absent from the pin | Bounded opaque relay only | Not active |
| Background operation | Native platform lifecycle | Native platform lifecycle | No; radio stops with the app | No |
| Production-signed distribution | Native project process | CI supports signed Release APK; local default is debug | CI supports signed portable package and installer; local default is unsigned | Development preview |

The shared contract contains every current Apple message and Noise payload
value. Automated tests compare it with the untouched Swift sources and verify
the smaller official Android subset. A complete wire contract therefore does
not falsely imply complete Desktop or Android application behavior.

## Security boundaries

- Windows Noise and Ed25519 private keys are generated by the native sidecar
  and stored with Windows DPAPI, scoped to the current user. Key material is
  never persisted in Web Storage by the packaged Desktop host.
- Electron uses context isolation, renderer sandboxing, origin checks and an
  owner check for every radio IPC operation.
- Public files require a valid announced Ed25519 identity and signature;
  private files travel inside an authenticated Noise session.
- Fragment counts, chunk sizes, assembled bytes, timestamps, duplicate IDs and
  relay TTL are bounded. Link-local sync requests are never relayed.
- Browser-only identity uses session storage because a normal Web page has no
  DPAPI port. It is useful for testing but is not equivalent to native secure
  storage.
- Passing protocol vectors and automated checks is not a substitute for an
  independent security audit.

## Validation snapshot

- Portable protocol/Web core: 31 tests pass, including media capture/optimization,
  native Noise/Nostr fixtures, Apple/Android contract checks and signed file transfer.
- Desktop host: 6 tests pass; the .NET sidecar builds with zero warnings and
  zero errors.
- Packaged Desktop smoke: loopback runtime starts, BLE advertising reaches
  `Started`, and identity protection reports `dpapi-current-user-v1`.
- Android: the universal debug APK packages successfully at pinned revision
  `49753ccb888531bfc413431e7002b0776a8268f0`; the checkout is clean.
- The pinned Android lint report still contains 273 errors and 333 warnings,
  and Windows unit runs retain upstream failures. These findings are not hidden
  or patched in the official checkout.
- Physical Windows-to-Android BLE interoperability still requires an
  authorized phone in range; it is not claimed by the local smoke test.
- GitHub workflows validate all three additive targets, scan JavaScript/C# with
  CodeQL and can publish hashed, attested prerelease assets. Signing and the
  physical release gate remain deployment requirements, not inferred results.
